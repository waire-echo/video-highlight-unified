# 接力、资源自适应和效果检查

下列GPU对照来自整理仓库前的接力实现。当前统一入口与新增的资源自适应调度仅完成本地工程验证，尚未做新的GPU端到端运行。

## 已做的实际对照

2026-10-02在同一4090上，对5个视频、1084个高光帧分别重新运行原慢速和接力流程。每组都使用全新检测、姿态和跟踪缓存。

| 指标 | 结果 |
|---|---:|
| 慢速耗时 | 75.867秒 |
| 接力耗时 | 60.061秒 |
| 耗时减少 | 约20.8% |
| 最终框完全相同 | 1075/1084帧（99.17%） |
| 其余框的最大坐标差 | 1像素 |
| 平均裁剪IoU | 0.999959 |
| 最低裁剪IoU | 0.995074 |
| 视频ID、画幅、高光帧号 | 完全相同 |

这是小样本工程对照，未证明全量逐位等价，也没有真实标注分数。不同batch的半精度推理可能出现细小浮点差异，再经取整形成1像素变化。

早期还检查了6个非连续真实帧的读取SHA一致，以及4条视频、971帧使用同一检测缓存后的串行/并行结果完全一致。这两项用于排除预读错序和合并错配，不能替代上面的重新推理对照。

## auto与compat

`compat` 使用原始batch8/4、单进程跟踪和原顺序读取，适合对照。

`auto` 在每次启动时根据GPU可用显存、可用内存与实际CPU配额选择batch、预读深度和最大跟踪并发。24GB GPU和15个CPU的参考计划为YOLO64、Pose32、最大3个跟踪进程。它不会为了提升利用率删帧、增大帧步长、改检测阈值或修改事件选择。

CPU先读取下一批帧，GPU处理当前批。跟踪按独立视频分配，同一视频的帧和轨迹仍保持原顺序。结果按原输入顺序合并，并校验帧集合与裁剪宽度。

## 运行时调节

跟踪任务拆成均衡的小组，每次准备启动新组时读取CPU/GPU占用：CPU压力达到90%、可用内存低于8GB或显存低于1.5GB时限制新的并发；GPU占用达到95%时减少新组并发。正在跟踪的视频不会被打断。

因此自适应发生在安全任务边界，不是根据某一帧的瞬时占用反复改变识别算法。短视频、CPU解码和轨迹后处理会产生GPU空档；任务完成后GPU负载回落到0%是正常现象。

`logs/adaptive_plan.json` 记录初始方案，`logs/resource_usage.jsonl` 每5秒记录资源，跟踪子目录的 `status.json` 记录当前并发限制和待处理组数。

## 自己做小样本验证

先生成第一阶段时间交接，或在配置中指定已有handoff，再执行：

```bash
python3.11 pipeline.py --config configs/pipeline.local.json verify-relay --video-ids 0,1,2
```

用自己的代表性ID替换上述示例，覆盖人物/动物、横版/竖版和空预测。工具输出三阶段差异、最终框IoU、最大像素变化和耗时；检查实际画面后再判断是否适合自己的数据。

每次对照使用独立目录和新缓存，不用全量慢速重跑。改变模型、精度或语义参数时应重新对照。
